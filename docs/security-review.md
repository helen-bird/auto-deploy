# 公开前安全审查

## 范围与结论

本次人工代码审查覆盖 Git 来源和 SHA 校验、只读检查、命令执行、服务安装权限、状态/锁、日志与健康检查，并使用自动化回归验证关键路径。未做独立渗透测试、第三方依赖漏洞数据库全量审计或所有 macOS 版本实机验收，不能作为无漏洞保证。

没有发现仅凭访问公开工具仓库、提交未合并 PR 或构造提交消息即可远程执行部署命令的路径。工具不提供监听外网的控制 API；自动检查只读取指定 main，执行部署需要显式调用 CLI 并通过完整 SHA、待审批记录和部署基线校验。仓库文本不是可信指令，自动化任务必须维持这一边界。

## 本次修复

- HTTP 健康检查拒绝重定向、禁用代理，限制响应为 64 KiB 并验证 JSON 对象，避免重定向误判及超大响应。分块读取期间检查总期限；单次阻塞读取仍受最多 5 秒的 socket 超时约束。
- 命令 stdout/stderr 合计超过 8 MiB 时终止进程组，避免无限缓存输出。失败进入现有部署恢复流程；不记录截断片段，避免破坏脱敏边界。
- watcher/deployment 日志加入轮转和单条记录上限；服务输出的单行长度也有限制。超长服务输出终止子进程，随后遵循 launchd 的既有重启策略。

## 仍然存在的风险

| 攻击者能力/条件 | 风险与边界 | 使用建议 |
|---|---|---|
| 业务 main 或依赖被攻陷，并被操作者批准 | 安装和业务代码能读部署用户文件、联网和产生外部副作用；非 root 不等于无害 | 专用普通用户，审查依赖、锁文件及版本；只部署可信代码 |
| 已控制部署用户或可写本地配置/状态/工具目录 | 可直接调用 CLI、修改审批状态或命令；本工具不是账号权限隔离层 | 保护用户账号和目录，不与不可信用户共享写权限 |
| 上游 main 包含海量 Git 对象/历史 | fetch 的网络、磁盘使用没有总配额，命令超时和输出限制不等于仓库存储配额 | 仅监控可信仓库，预留并监测磁盘空间；高风险环境另设系统配额 |
| 应用持续产生超长日志或故意崩溃 | 虽已限制日志/内存输出，仍可造成重启循环或 CPU 压力；任意业务进程没有总内存/CPU配额 | 监控服务故障；不要运行不可信工作负载 |
| 应用输出经编码、拆分的密钥 | 通用日志脱敏无法识别所有变体 | 应用本身不得输出秘密，提交工单前再次脱敏 |
| 应用实施不可逆数据库迁移 | 代码回滚不能恢复数据库或撤销外部调用 | 部署步骤兼容回滚，并独立备份业务数据 |

健康检查只能验证配置中的有限健康条件，不能证明代码可信或业务完整正确。HTTP 检查依赖本机端口归属；其他本地进程若能占用同一端口，可能伪装健康服务。建议使用专用账号和业务特有的健康验证。

现有防护还包括禁止 Git hooks/fsmonitor/ext 协议、禁用 diff 外部命令及 textconv、拒绝脏工作树、主分支来源校验、限定服务的 sudoers 命令和非 root 服务用户。它们减少误操作和部分攻击面，但不能防御已获本地同用户权限或已批准的恶意业务代码。
